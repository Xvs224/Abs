# 异常检测模块 — 运行逻辑与实现方法

## 一、模块定位与设计目标

异常检测是毕业论文质量监控系统的**核心功能**，负责对论文全过程（选题 → 开题 → 中期 → 论文 → 评阅答辩）中产生的数据进行自动扫描，识别偏离群体分布的离群样本，辅助教师和管理员及时发现进度滞后、质量异常、评分偏差等问题。

**设计目标：**
- **全链路覆盖**：6 类检测对象（学生、选题、开题、中期、论文、评阅），每类对应一组特征。
- **双算法融合**：IQR 四分位距（统计方法，可解释性强）+ 孤立森林（机器学习方法，多维协同），采用"并集判定 + 加权评分"组合。
- **可人工复核闭环**：检测结果落地为异常记录，支持人工复核（确认/误报/忽略/已处理），形成"检测 → 复核 → 沉淀"闭环。
- **准确性可评估**：内置评估器，基于模拟数据集输出精确率、召回率、F1 等指标，便于调参。

## 三、特征工程

### 3.1 检测对象与特征映射

`anomaly_engine.py` 中维护 `TARGET_FEATURE_MAP`，定义了 6 类对象各自的可检测特征及异常方向：

| 对象类型 | 特征名 | 说明 | 异常方向 |
|---------|--------|------|---------|
| **student** | progress_percentage | 进度百分比 | 偏低 |
| | thesis_version_count | 论文版本数 | 双向 |
| | format_score | 格式得分 | 偏低 |
| | word_count | 论文字数 | 双向 |
| | review_score_deviation | 评阅分数偏差 | 偏高 |
| | rectification_count | 整改数量 | 偏高 |
| **topic** | topic_difficulty / topic_workload | 难度/工作量 | 双向 |
| **proposal** | proposal_word_count / proposal_references_count | 字数/参考文献数 | 双向 |
| **midterm** | progress_percentage / midterm_score / midterm_score_deviation / rectification_count | 进度/成绩/评分偏差/整改数 | 低/低/高/高 |
| **thesis** | thesis_version_count / format_score / word_count / reference_count | 版本数/格式/字数/参考文献 | 双/低/双/低 |
| **review** | review_avg_score / review_score_deviation / defense_score / review_defense_deviation | 平均分/分差/答辩/评阅答辩差 | 低/高/低/高 |

> **异常方向**约束了检测只关注特定方向的离群：例如"格式得分"只检测**偏低**（得分低才是异常），"整改数量"只检测**偏高**（整改多说明问题多）。

### 3.2 特征提取器 `FeatureExtractor`

文件：`backend/app/anomaly/feature_extractor.py`

针对每类对象提供一个 `extract_*_features(db, id)` 方法，从多张业务表中聚合数据：

- **`extract_student_features`**：以学生为中心，串联其选题 → 中期 → 论文 → 评阅数据，形成全过程特征向量。
- **`extract_thesis_features`**：取该选题下论文版本总数、最新版本的格式检测得分（`FormatCheck.total_score`）、字数、参考文献数等。
- **`extract_midterm_features`**：进度百分比、教师/检查组评分偏差（`|teacher_score - check_group_score|`）、整改项数。
- **`extract_review_features`**：评阅平均分、不同评阅教师间最大分差、答辩成绩、评阅-答辩分差。

`features_to_vector()` 将特征字典按固定 key 顺序转为数值向量，供孤立森林使用。缺失值统一填 0.0。

## 四、检测算法

### 4.1 IQR 四分位距检测器

文件：`backend/app/anomaly/iqr_detector.py`

**原理**：对每个特征，收集同类所有目标的该特征值，计算 Q1（25% 分位）、Q3（75% 分位）、IQR = Q3 - Q1。异常判定：

```
下界 = Q1 - k * IQR
上界 = Q3 + k * IQR
异常 ⟺  value < 下界  或  value > 上界
```

其中 `k = ANOMALY_IQR_THRESHOLD = 1.5`（标准异常阈值）。

**异常分数**（归一化到 0~1）：
```
deviation = |value - 边界| / IQR
score = min(1.0, deviation / 3.0)
```
即偏离边界 3 倍 IQR 即记满分（最异常）。

**严重等级**：

| 分数范围 | 等级 |
|---------|------|
| ≥ 0.7 | L3 告警（重度） |
| 0.4 ~ 0.7 | L2 警告（中度） |
| 0 ~ 0.4 | L1 提示（轻度） |

**方向过滤**：若特征方向为 `low`，只保留 `position == "low"` 的异常；为 `high` 同理。

### 4.2 孤立森林检测器

文件：`backend/app/anomaly/isolation_forest_detector.py`

**原理**：基于 `sklearn.ensemble.IsolationForest`。异常样本在随机划分的孤立树中路径更短，更容易被"孤立"。

**关键参数**（可在 `config.py` 调整）：
- `contamination = 0.1`：预期异常比例 10%（样本少时自动下调，保证至少能标记 1 个异常）
- `n_estimators = 100`：孤立树数量
- `random_state = 42`：可复现

**分数归一化**：sklearn 的 `decision_function` 返回 `[-0.5, 0.5]`，负值为异常。通过 sigmoid 映射到 `[0, 1]`：

```python
normalized = 1.0 / (1.0 + exp(raw_score * 10))
```
> raw_score 越负（越异常），normalized 越接近 1。

### 4.3 组合检测（默认方法 combined）

文件：`anomaly_engine.py` 的 `_detect_combined`

```
is_anomaly = IQR异常  OR  孤立森林异常        # 并集策略，提高召回率
combined_score = IQR分数 * 0.4 + 孤立森林分数 * 0.6   # 加权
等级 = score≥0.7→L3 / ≥0.4→L2 / >0→L1
置信度 = 两法一致? min(0.95, max+0.1) : max*0.7
```

> 孤立森林权重更高（0.6），因为其考虑多维联合分布；IQR 负责提供可解释的特征级详情。

## 五、检测流程

### 5.1 单次检测 `detect_target(type, id, method)`

```
1. 校验 type 是否在 supported_target_types 中
2. FeatureExtractor 提取目标特征 target_features
3. _get_all_features_by_type(type) 提取所有同类目标特征作为参考集
4. 参考集为空 → 返回"参考数据不足"
5. 根据 method 分发：
   - iqr             → _detect_by_iqr(target, all, type)
   - isolation_forest→ _detect_by_isolation_forest(target, all, type)
   - combined        → _detect_combined(target, all, type)
6. 补充 target_type / target_id / method / feature_data 后返回
```

### 5.2 批量检测 `detect_batch(type, method)`

- **IQR**：逐个对每个样本调用 `_detect_by_iqr`。
- **孤立森林**：一次性构建特征矩阵，`fit` 后 `predict(X_all)` 批量输出。
- **combined**：逐个调用 `_detect_combined`。

### 5.3 全量检测 `run_full_detection()`

遍历 6 种 `target_type`，对每种调用 `detect_batch(type, "combined")`，汇总：
```
summary = {
  total_targets, total_anomalies, L1_count, L2_count, L3_count,
  by_type: { student: {total, anomalies, L1, L2, L3}, ... }
}
```
对每个检测为异常的结果，调用 `save_anomaly_record()` 持久化。

### 5.4 异常记录持久化 `save_anomaly_record`

从检测结果中提取最异常的特征（按 score 排序取第一），生成：
- **`description`**：如"论文版本数偏高，另有1项指标异常"
- **`suggestion`**：根据异常特征和等级生成可操作建议，如"论文格式不规范，需按照模板认真修改"

写入 `anomaly_records` 表，初始 `review_status = "pending"`。

## 六、复核闭环

### 6.1 数据模型

**`anomaly_records`**（异常记录）：
- `severity_level`：L1/L2/L3
- `review_status`：`pending` 待复核 → `confirmed` 确认异常 / `false_positive` 误报 / `ignored` 忽略 / `resolved` 已处理

**`anomaly_reviews`**（复核流水）：
- `result`：复核结论
- `opinion`：复核意见
- `reviewer_id` / `review_time`

### 6.2 复核接口

`POST /api/anomaly/records/{id}/review`，请求体：
```json
{ "result": "confirmed", "opinion": "确实进度严重滞后" }
```

服务层 `review_record`：
1. 更新 `anomaly_records.review_status = result`、`reviewer_id`、`review_time`、`review_opinion`
2. 新增一条 `anomaly_reviews` 流水（支持多次复核的历史追溯）

### 6.3 前端复核交互

- 列表中 `review_status === 'pending'` 的记录显示"复核"按钮。
- 复核弹窗三个选项：确认异常 / 忽略误报 / 已处理，提交后刷新列表与统计。
- 详情弹窗底部"复核历史"时间线展示历次复核记录（复核人、结果、意见、时间）。

## 七、准确性评估

文件：`backend/app/anomaly/evaluator.py`

### 7.1 测试数据生成

`generate_test_data(normal=80, critical=10, abnormal=10)`：
- **正常样本**：各特征按 `FEATURE_NORMAL_RANGES` 中定义的 (均值, 标准差) 正态采样。
- **临界样本**：各特征向异常方向偏移 1.5σ（接近 IQR 边界）。
- **异常样本**：随机选 2~4 个特征，向异常方向偏移 3.5σ。

### 7.2 评估指标

`evaluate(y_true, y_pred, scores)` 计算混淆矩阵及：

| 指标 | 公式 |
|------|------|
| 准确率 accuracy | (TP+TN) / N |
| 精确率 precision | TP / (TP+FP) |
| 召回率 recall | TP / (TP+FN) |
| F1 | 2·P·R / (P+R) |
| 误报率 false_alarm_rate | FP / (FP+TN) |
| AUC | Mann-Whitney U 近似（梯形法累加 ROC 曲线面积） |

### 7.3 评估入口

`POST /api/anomaly/evaluate`，body 可空（默认 `dataset_type=all, method=combined`），返回上述指标。前端将 `precision/recall/f1_score`（0~1 浮点数）×100 后以百分比展示。

> 另提供 `evaluate_with_real_data`：基于已复核记录（`confirmed`=TP, `false_positive`=FP）计算精确率，作为真实场景下的参考。

## 八、数据隔离（权限）

异常检测接口遵循系统角色权限模型：

| 接口 | 权限 | 数据范围 |
|------|------|---------|
| `POST /detect` | `require_teacher_or_admin` | 教师可测自己学生，管理员全量 |
| `GET /records` | 任意登录用户 | 管理员全量；教师仅自己负责的学生；学生仅自己 |
| `GET /records/{id}` | `require_student_or_teacher` | 学生只能看自己的 |
| `POST /records/{id}/review` | `require_teacher_or_admin` | 教师/管理员复核 |
| `GET /stats` | `require_teacher_or_admin` | 教师按自己学生过滤 |
| `POST /evaluate` | `require_admin` | 仅管理员 |

教师数据隔离通过 `_get_teacher_student_ids(db, teacher_id)` 获取该教师所有选题对应的 `student_id` 列表实现。

## 九、关键配置

`backend/app/config.py`：

```python
ANOMALY_IQR_THRESHOLD: float = 1.5              # IQR 倍数阈值
ANOMALY_ISOLATION_FOREST_CONTAMINATION: float = 0.1  # 孤立森林预期异常比例
```

**调参建议**：
- 若误报过多 → 调高 `ANOMALY_IQR_THRESHOLD` 至 2.0~3.0，或降低 `contamination`。
- 若漏报过多 → 调低 `ANOMALY_IQR_THRESHOLD`，或调高 `contamination`。
- 样本量极小时孤立森林自动下调 `contamination` 到 `max(1/n, 0.5)`。

## 十一、运行时调用链（以"触发检测"为例）

```
用户点击 [触发检测]
  │
  ▼
frontend: detectAnomaly({}) → POST /api/anomaly/detect  (body={})
  │
  ▼
api/anomaly.py: detect_anomaly()
  ├─ Depends(require_teacher_or_admin)  权限校验
  ├─ target_type 为空 → service.run_full_detection()
  │
  ▼
anomaly_service.run_full_detection()
  └─ engine.run_full_detection()
       ├─ for type in [student, topic, proposal, midterm, thesis, review]:
       │    engine.detect_batch(type, "combined")
       │      ├─ _get_all_features_by_type(type)  ← FeatureExtractor 拉取全部同类特征
       │      └─ for feat in all_features:
       │           _detect_combined(feat, all_features, type)
       │             ├─ _detect_by_iqr()           ← 逐特征 IQR
       │             └─ _detect_by_isolation_forest()  ← sklearn IF
       │      → 保存异常记录到 anomaly_records
       └─ 返回 summary
  │
  ▼
返回 { summary: {total_targets, total_anomalies, L1/L2/L3, by_type} }
  │
  ▼
前端 ElMessage.success("检测任务已启动") → loadList() + loadStats() 刷新
```

## 十二、可扩展点

1. **定时自动检测**：可接入 APScheduler，按 cron 周期调用 `run_full_detection`，实现无人值守巡检。
2. **告警推送**：检测到 L3 异常时，通过系统通知/邮件/飞书主动推送给指导教师。
3. **规则引擎扩展**：`TARGET_FEATURE_MAP` 增加新特征只需改字典，无需改算法。
4. **真实数据评估**：积累足够已复核记录后，用 `evaluate_with_real_data` 替代模拟数据评估，反映真实准确率。
